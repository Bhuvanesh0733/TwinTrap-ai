# TwinTrap AI — Digital Twin Drift Detection

**Detecting and Explaining Digital-Twin Divergence Using Machine Learning**

TwinTrap AI is an academic ML project (Advanced Machine Learning assignment) built as a full-stack
application — a Python/FastAPI backend and a React/Vite/Tailwind frontend — with two demonstration modes:

1. **Industrial Twin Simulation** — a simulated industrial motor and its Digital Twin, used for the
   core ML experiments (PCA, SVD, LDA, four classifiers, hyperparameter tuning, class-imbalance
   experiments, SHAP explainability).
2. **Smartphone Live Twin** — a real Android/iPhone used as a live physical demonstration of the same
   concept (physical system → telemetry → Digital Twin → discrepancy → ML → explanation), for
   presenting the project in person.

No Streamlit. No notebooks pretending to be a product. A real client/server application, run locally.

**Live Demo →** [https://twin-trap-ai.vercel.app/](https://twin-trap-ai.vercel.app/)

---

## 1. Project overview

A Digital Twin is a computational model that predicts the expected state of a physical system. Over
time, a twin can silently drift away from the system it represents — because of unmodeled physics,
sensor faults, wear, or a shift into an operating regime the twin was never calibrated for. TwinTrap AI
asks whether machine learning can detect that divergence from sensor **discrepancy features** alone, and
explain *why* it made that call.

## 2. Motivation

Digital twins are increasingly used for predictive maintenance and industrial monitoring, but a twin that
has silently desynchronized from reality is worse than no twin at all — it produces confident, wrong
predictions. Automatically flagging *when a twin can no longer be trusted*, and explaining which sensors
are responsible, is the practical problem this project targets.

## 3. Research question

> Can a lightweight machine-learning system detect and explain Digital Twin divergence using sensor
> discrepancy features while maintaining reliable performance under class imbalance?

See `docs/research_gap.md` and the in-app **Research / Case Study** page for the full sub-questions.

## 6. Dataset

**No fabricated claim of a public dataset is made.** Before building the simulation we looked for a
public digital-twin / predictive-maintenance dataset (e.g. NASA C-MAPSS, AI4I 2020, CWRU bearing data).
None of these provide what this project specifically needs: **paired physical-system and digital-twin
sensor streams with controllable, labeled drift events** — that pairing is inherent to the *comparison*
this project studies, not something a static public dataset captures. Per the assignment's own fallback
clause, we instead built a **documented, physically-motivated simulation** (not random Gaussian noise —
see §7) and labeled every row's provenance:

| `source` value | Meaning |
|---|---|
| `simulation` | Every row in this project — generated by the coupled machine/twin physics model |
| (injected drift) | `drift_type`, `drift_severity_value`, `operating_condition` columns record exactly what was injected and when |

This distinction (`SIMULATED` vs `PUBLIC DATASET` vs `INJECTED DRIFT` vs `MODEL PREDICTION` vs
`GROUND TRUTH`) is preserved end-to-end: in the dataset itself, in the API responses, and in the UI.

## 7. Data generation (industrial machine)

`backend/app/simulation/physics.py`, `machine.py`, `twin.py` implement a coupled, non-linear model of an
industrial motor: load drives RPM → torque → current → (vibration, temperature via a first-order thermal
integrator) → pressure. The Digital Twin runs a **simplified, linearized** version of the same equations
— exactly like a real reduced-order twin — so a small residual discrepancy exists even when "healthy",
and grows sharply outside the twin's calibrated operating envelope. See the module docstrings for the
exact equations and constants.

## 8. Drift generation

`backend/app/simulation/drift.py` implements all 8 required scenarios (gradual, sudden, temperature,
vibration, rpm, multi-sensor, noise, operating-condition-shift) as fault events applied to the **real**
machine only — the twin never sees them, which is exactly why divergence appears. Every fault has a
time-varying magnitude `m(t) ∈ [0,1]`; a row is labeled `DRIFT` iff `m(t)` exceeds a single documented
threshold (`CFG.drift_label_threshold = 0.15`), so gradual-drift episodes naturally contain both healthy
and drifted rows as the fault ramps up.

## 9. Preprocessing

`backend/app/ml/preprocessing.py`: missing-value drop, duplicate removal, IQR outlier clipping **fit on
train only**, `StandardScaler` **fit on train only**, stratified train/val/test split, optional class
weighting, optional SMOTE (fit on train only — see `apply_smote`). The test split is never touched during
fitting or hyperparameter search.

## 10. PCA

`backend/app/ml/pca_svd.py::run_pca` — `sklearn.decomposition.PCA`, reported as explained variance ratio
per component, cumulative explained variance, and a PC1/PC2 scatter (healthy vs drift), fit on the train
split. Surfaced on the **PCA / SVD / LDA Lab** page.

## 11. SVD

`backend/app/ml/pca_svd.py::run_svd` — an **explicit** `U, S, Vt = np.linalg.svd(X_scaled, full_matrices=False)`,
not hidden inside PCA. Reports `U.shape`, `S.shape`, `Vt.shape`, the singular values, and cross-checks
that `S**2/(n-1)` reproduces sklearn's PCA explained variance ratio (`matches_pca` field).

## 12. LDA (supervised complement to PCA/SVD)

`backend/app/ml/lda.py` — `sklearn.discriminant_analysis.LinearDiscriminantAnalysis`, reporting the 1D
LD1 projection, class means, and Fisher's separation ratio (between-class / within-class variance) — all
computed, not asserted.

## 13. Models

Logistic Regression, Random Forest, XGBoost (falls back to `GradientBoostingClassifier` with a labeled
substitution if XGBoost is unavailable — see `ml/classifiers.py`), and an MLP. Every model implements
`fit` / `predict` / `predict_proba`.

## 14. Hyperparameter tuning

`backend/app/ml/tuning.py` — `GridSearchCV` and `RandomizedSearchCV` on Random Forest / XGBoost, small
bounded search spaces (12 combinations), 3-fold `StratifiedKFold`, scored on F1. Reports the search space,
number of combinations/iterations, best params, best CV score, and final test-set performance (scored
once, after search, never used to pick hyperparameters).

## 15. Cross-validation & learning curves

`ml/cross_validation.py` (explicit k-fold `cross_validate`, separate from its internal use inside
GridSearchCV) and `ml/learning_curve.py` (`sklearn.model_selection.learning_curve`), both on the train
split. Surfaced on the **Model Lab** page.

## 16. ROC-AUC

`backend/app/evaluation/metrics.py::roc_curve_data` — `roc_curve` + `roc_auc_score`, plotted against the
diagonal baseline, with an in-app explanation of what ROC does and doesn't tell you.

## 17. Precision-Recall

`evaluation/metrics.py::pr_curve_data` — `precision_recall_curve` + `average_precision_score`, plotted
against the dataset's drift prevalence as baseline.

## 18. Class imbalance

Four configurations — Balanced (50:50), Moderate (90:10), High (95:5), Severe (99:1) — built by
stratified resampling from the same simulated pool (`simulation/dataset_generator.py::resample_to_ratio`).
`evaluation/imbalance_experiment.py` retrains **one fixed model configuration** (Random Forest, same
hyperparameters) across all four and **programmatically generates** the interpretation text (which metric
moved more, ROC-AUC vs Average Precision) from the actual numbers — never hardcoded. See the
**Evaluation** page.

## 19. SHAP

`backend/app/ml/shap_explain.py` — `TreeExplainer` for tree models, `LinearExplainer` for Logistic
Regression, a small-sample `KernelExplainer` fallback for the MLP. Global importance (mean |SHAP value|
over a sample) and local, per-sample explanations (top contributors with signed SHAP values) are both
computed from the actual fitted model — never fabricated. The smartphone mode gets its own, separately
documented SHAP path (§21).

## 20. Twin Fidelity

**Industrial twin** (`backend/app/utils/fidelity.py`):

```
normalized_discrepancy_i = min(|real_i − twin_i| / SCALE_i, 1.0)     for each of the 6 sensors
TWIN FIDELITY (%) = 100 × (1 − mean_i(normalized_discrepancy_i))
```

`SCALE_i` (documented per-sensor "complete loss of fidelity" magnitude) is calibrated from the same
fault-magnitude bounds used in `drift.py`. Drift **severity** (`LOW/MEDIUM/HIGH/CRITICAL`) is derived from
the ML model's predicted drift probability via a fixed, documented threshold table
(`utils/fidelity.py::SEVERITY_THRESHOLDS`).

**Smartphone twin** (`backend/app/simulation/mobile_twin.py`) uses the same "1 − normalized discrepancy"
family of formula, but normalized in units of the *device's own calibrated standard deviation* per
channel (with a documented "free zone" so ordinary sensor noise doesn't itself count as drift) — see
`FREE_ZONE_STD` / `FULL_LOSS_STD` and the severity bands `SYNCHRONIZED / MINOR_DIVERGENCE /
SIGNIFICANT_DIVERGENCE / CRITICAL_DIVERGENCE`.

## 21. Smartphone Live Demonstration

A **separate, clearly-labeled** pipeline ("Smartphone Cyber-Physical Demonstration") lets you use a real
phone as the physical asset:

```
Phone (DeviceMotionEvent) --WebSocket--> FastAPI (/ws/mobile-sensor)
   --> per-device MobileTwinSession --> calibration baseline (Expected State)
   --> discrepancy features vs Observed State --> Twin Fidelity + severity
   --> Smartphone Divergence Model (RandomForest, trained on synthetic
       archetypes anchored to THIS device's own calibration stats)
   --> on-demand SHAP explanation --> Desktop dashboard (/smartphone)
```

The industrial model is **never** silently applied to phone data — the feature spaces are incompatible by
design, so the smartphone mode has its own model, trained fresh after each calibration (see
`simulation/mobile_twin.py` docstring for exactly why and how).

### Running the demo

1. **Start the backend, bound to the network** (not just localhost):
   ```bash
   cd backend
   source venv/bin/activate        # or: venv\Scripts\activate on Windows
   uvicorn app.main:app --host 0.0.0.0 --port 8000
   ```
2. **Start the frontend**, already configured to bind to `0.0.0.0` in `vite.config.js`:
   ```bash
   cd frontend
   npm run dev
   ```
3. **Find this laptop's local IP address** (phone and laptop must be on the same Wi-Fi):
   - **Windows**: open Command Prompt, run `ipconfig`, look for "IPv4 Address" under your active
     Wi-Fi adapter (e.g. `192.168.1.23`).
   - **macOS**: System Settings → Wi-Fi → Details, or run `ipconfig getifaddr en0` in Terminal.
   - **Linux**: run `hostname -I` or `ip addr show`.
4. On the phone, open `http://<that-ip>:5173/mobile`.
5. Tap **Enable Motion Sensors** (grants the browser motion permission; required on iOS Safari).
6. Tap **Start Telemetry**. The laptop's **Smartphone Live Twin** page (`/smartphone`) should show
   "Phone Connected" within a second.
7. Keep the phone still and tap **Calibrate Twin** — wait for "Twin Calibration: COMPLETE".
8. Move/rotate/shake the phone — watch the live charts and Twin Fidelity respond.
9. On the laptop, use **Inject Drift** to demonstrate `SIMULATED SENSOR DRIFT` (bias / spike / gradual /
   noise / multi-sensor) layered on top of the real incoming values — clearly labeled as simulated, never
   presented as a real sensor failure.
10. Tap **Explain Current Prediction** to see the SHAP-based explanation of the current divergence score.

No IP address is hard-coded anywhere in the app — `frontend/src/services/api.js` derives the backend's
address from `window.location.hostname`, so the same build works from `localhost` on the laptop and from
the LAN IP on the phone.

**Browser support**: motion sensors require `DeviceMotionEvent` — supported on Chrome/Firefox for
Android and Safari for iOS 13+ (which additionally requires the explicit **Enable Motion Sensors** tap to
grant permission, since iOS blocks motion access without a user gesture). Desktop browsers without a
motion sensor will show "This browser doesn't expose DeviceMotionEvent."

**Privacy**: only accelerometer/gyroscope values are read. No contacts, photos, messages, or microphone
access is requested, and nothing is persisted to disk unless you explicitly add recording (not enabled by
default).

## 22. Experimental methodology

Fixed random seed (`42`) throughout. Every `POST /api/train` run persists its scaler, fitted models, and
a JSON snapshot of the exact dataset configuration + results to `backend/experiments/run_<timestamp>/`,
so any number shown in the UI is traceable to the run that produced it. See `docs/experiments.md`.

**Requirements**: Python 3.10+, Node.js 18+.

```bash

cd backend
python3 -m venv venv
source venv/bin/activate            # Windows: venv\Scripts\activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000

# Frontend (new terminal)
cd frontend
npm install

```

Open `http://localhost:5173`. The backend trains an initial model on startup, so the Dashboard,
Evaluation, and Explainability pages have real data immediately.

## 24. Limitations

- The industrial machine and every fault are **simulated**, not measured from real hardware — see §6.
- The literature review is a placeholder (§4) — no research-gap claim should be treated as validated
  until Paper A / Paper B are supplied.
- The smartphone divergence model is trained on synthetic archetypes anchored to a device's own
  calibration statistics, not on real labeled phone-drift incidents (none exist for an ad-hoc demo) — it
  is a statistically-grounded stand-in, documented as such everywhere it's surfaced.
- Class-imbalance experiments resample from one simulated pool; extreme ratios draw more from the
  available minority rows, which is recorded (`bootstrapped_minority`) rather than hidden.

## 26. Ethical considerations

This is a simulated system; no claims are made about any specific real machine, vendor, or deployed
digital twin. Automated drift/anomaly alerts should support, not replace, qualified human judgement —
especially for CRITICAL-severity actions. Model outputs (probabilities, SHAP attributions) are statistical
explanations of a fitted classifier, not certified diagnostic conclusions. The smartphone mode requests
only the motion/orientation data required for the demo and stores nothing by default.
